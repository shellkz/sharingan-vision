# 辨識服務部署方案

有兩個獨立的決策維度,不要混在一起看:

- **維度 A:要不要具備「運作中優化」(特徵池)能力**——服務要不要有資料庫,predict 能力會不會隨著新增/修正參考圖持續進化
- **維度 B:(只有維度 A 選「要」才需要決定)特徵池要存在哪種資料庫**——Postgres 或 SQLite

維度 B 是維度 A 底下的子選擇,不是跟維度 A 平行的另一條線——選了「不要資料庫」,維度 B 就不存在。

## 選項 1(維度 A = 不要):純無狀態辨識,沒有資料庫

服務只提供 `/predict`,吃圖輸出判斷結果,catalog 是靜態的(例如開機讀一次 `catalog.json`),完全沒有運作中優化能力。這是最單純的形態,連 SQLite 都不需要。

```
vision-service (FastAPI + ONNX + 靜態 catalog.json)
```

### 第三方開發者設定步驟

1. 拿到辨識服務的 image + docker-compose 範例(一個 service 區塊)
2. 貼進自己的 `docker-compose.yml`:設定模型路徑環境變數,掛載模型檔案 volume
3. 沒有 catalog 動態更新這回事——新增/修改品項的參考圖,需要離線重新產生 `catalog.json`、重新部署整個服務(改檔案、重啟 container)
4. 自己的程式打 `POST /predict`,拿 JSON 結果

## 選項 2(維度 A = 要,維度 B = SQLite):特徵池存 SQLite

`recognition_entities`/`recognition_embeddings`(見 `docs/schema.md`)存在 SQLite 檔案裡,跟著 vision-service 這個 container 一起打包,沒有額外的資料庫 process。讀取路徑建議不做記憶體快取(每次請求直接查,DINOv2 推論本身就要 1 秒多,查詢開銷可忽略),順便繞開快取何時失效的問題。

```
vision-service (FastAPI + ONNX + SQLite 檔案)
```

### 第三方開發者設定步驟

1. 拿到辨識服務的 image(`ghcr.io/shellkz/sharingan-vision:<版本>`)+ docker-compose 範例(一個 service 區塊)
2. 去 [Release 頁面](https://github.com/shellkz/sharingan-vision/releases)下載對應版本的模型檔案(`FastSAM-s_640_fp32.onnx`、`dinov2_vits14_batch_int8.onnx`),放進自己專案裡準備掛 volume 的那個資料夾(例如 `./models/`)——**模型檔案不含在 image 裡**,這步是手動的,不會自動抓
3. 貼進自己的 `docker-compose.yml`:設定模型路徑環境變數、產生並設定 `VISION_API_KEY`(見 `docs/辨識服務API.md`「認證」,自己 `openssl rand` 產生,跟自己的 app service 共用同一個值),掛載模型檔案 volume + SQLite 檔案的 volume + 兩個圖片儲存 volume(`/app/data/samples/` 參考圖、`/app/data/scans/` 掃描圖,見 `docs/schema.md`)——都是為了確保 container 重啟資料還在

   ```yaml
   services:
     vision-service:
       image: ghcr.io/shellkz/sharingan-vision:v0.1.0
       environment:
         - FASTSAM_ONNX_PATH=models/FastSAM-s_640_fp32.onnx   # 容器內相對路徑(WORKDIR=/app)
         - DINOV2_ONNX_PATH=models/dinov2_vits14_batch_int8.onnx
         - VISION_API_KEY=${VISION_API_KEY}
       volumes:
         - ./models:/app/models      # 步驟 2 下載的模型檔案放這裡
         - ./vision_data:/app/data   # SQLite + samples/scans,不掛的話重啟資料就沒了
   ```

4. SQLite 檔案由 vision-service 自己在啟動時初始化,不用另外接資料庫、不用另外跑 migration
5. 餵自己領域的參考圖,透過 API 建立/更新 entity/instance,馬上生效,不用重啟服務;`score_threshold` 等判定參數也能透過 `PATCH /config` 現場調
6. 自己的程式帶 `Authorization: Bearer <key>` header 打 `POST /recognize`,拿 JSON 結果

## 選項 3(維度 A = 要,維度 B = Postgres):特徵池存 Postgres

跟選項 2 同樣具備運作中優化能力,但 `recognition_entities`/`recognition_embeddings` 存在獨立的 Postgres 實例,用 Alembic 管理 schema。

```
vision-service (FastAPI + ONNX)
vision-postgres (Postgres 16)
```

### 第三方開發者設定步驟

1. 拿到辨識服務的 image + docker-compose 範例(vision-service、vision-postgres 兩個 service 該怎麼接)
2. 把兩個 service 區塊貼進自己的 `docker-compose.yml`:設定模型路徑環境變數、DB 連線字串,掛載模型檔案 volume,確保跟自己的 app 在同一個 Docker network 上
3. 跑一次 `alembic upgrade head`(或等價指令)初始化 vision-postgres 的 schema
4. 餵自己領域的參考圖,透過 API/CLI 建立/更新 catalog,馬上生效,不用重啟服務
5. 自己的程式打 `POST /predict`,拿 JSON 結果

## 比較表

| 維度 | 選項 1:無狀態(無 DB) | 選項 2:SQLite | 選項 3:Postgres |
|---|---|---|---|
| **設定難度** | 最低:一個 service,無資料庫設定 | 低:一個 service,無需另外接 DB/跑 migration | 較高:兩個 service,要設定連線字串、跑 migration,容易在網路名稱/密碼/schema 版本同步上出錯 |
| **記憶體用量** | 最低,沒有任何資料庫層 | 低,SQLite 檔案本身幾乎不佔額外記憶體 | 較高,但增量不大——實測這台機器 postgres 剛啟動、無負載時約 **+27.9 MiB** |
| **獨有的功能** | 完全無共享狀態,水平擴展最容易(多開幾個 instance 互不干擾),部署/除錯最單純 | 部署單純(單一 container、單一檔案),備份/搬遷就是複製一個檔案,仍具備運作中優化能力 | 支援多個 vision-service 實例安全並發寫入同一份 catalog;完整交易保護;之後要接其他關聯式查詢/整合更自然 |
| **犧牲什麼** | 沒有運作中優化能力——新增/修改品項要離線重建 catalog、重新部署,不滿足硬要求 1 | 高頻並發寫入場景下(多實例同時大量新增樣本)可能碰到 SQLite 寫入鎖定的限制,但這對「偶爾新增參考圖」這種低頻寫入的實際使用情境影響不大 | 部署複雜度、多一個可能故障的環節、schema 版本要跟著服務更新持續同步維護 |

## 結論:採用 SQLite(選項 2)

現在的資料規模(幾十到幾千筆向量)遠低於需要 Postgres/pgvector 索引優化的量級,選項 3 的獨有優勢(多實例並發寫入、pgvector 索引)在這個專案的實際需求下用不到,不值得為此背負額外的部署複雜度。選項 1(無狀態)又不滿足「運作中優化」這個硬要求。單一 self-contained container、免資料庫連線設定,也最符合這個專案一路以來的瘦身方向(拿掉 YOLO/torch/opencv、模型量化、降解析度)。

**已驗證:拿掉 postgres 沒有讓 batch 推論變得有利**。postgres 已經從這個專案的 docker-compose 移除(container + `postgres_data` volume 都清掉了),辨識服務現在是真正單一、無資料庫依賴的 container。移除後重新對照過一次 batch vs sequential:sequential 約 1.5-1.7 秒、batch 約 1.8-2.0 秒,batch 依然沒有優勢,結論跟 postgres 還在跑的時候一致——之前猜測的「postgres 背景心跳污染 L3 cache」效應,即使存在,量級也不足以改變 batch/sequential 的相對結論。詳見 `docs/影像辨識.md` 的「FastAPI 化」章節。

## 本機測試指令(cmd.exe)

選項 2(SQLite)實際跑起來的 build/run 指令,`models/`、`data/` 兩個資料夾用 bind mount 掛進去(不是 image 裡建的,見上方「第三方開發者設定步驟」),`.env` 用 `--env-file` 直接引用、不用一個個手動餵環境變數:

```cmd
cd vision-service

docker rm -f vision-service

docker build -t vision-service .

docker run -d --rm -p 8000:8000 --env-file .env ^
  -v "%cd%\models:/app/models" ^
  -v "%cd%\data:/app/data" ^
  --name vision-service ^
  vision-service

docker logs -f vision-service
```

`docker rm -f` 那行是為了讓這組指令可以重複執行(改完程式碼要重新 build+run 時,舊 container 還在跑的話 `--name` 會撞名字);第一次跑、或上次是正常結束的話這行會印 `Error: No such container`,可以忽略。
