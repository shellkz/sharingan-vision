# 決策紀錄

FastSAM(objectness)+ DINOv2(embedding)few-shot 物件辨識測試專案的目前決策與已試過的方案。

## 整體流程的物理意義(不是實作細節)

分四個獨立、串接起來的問題,不要混在一起想:

**第一步(FastSAM/objectness):「這張圖裡有幾個獨立的物體、各自在哪裡?」**
不看物體是什麼,只看「這是不是一個跟背景/其他東西分得開的完整物件」——類似人眼掃過一張桌面照片,不用知道每個東西叫什麼名字,也能圈出「這裡有一個東西」的範圍。FastSAM 是通用模型,沒有針對特定物件訓練過,靠的是「物件通常有清楚邊界、跟背景質地不同」這種泛化的視覺先驗,不是查表比對。
大致上怎麼做:先讓 FastSAM 框出所有「看起來像一個物件」的候選框(同一張圖常常抓到幾十個,包含很多雜訊);把太不確定、或者跟別的候選框幾乎完全重疊(同一個物件被框了兩次)的先濾掉;剩下的框裡,常常還有「一個物件的完整範圍」跟「這個物件裡面某個顯眼小細節」各自被當成獨立候選框的情況(例如整支夾子是一個候選框,夾子中間的縫隙又是另一個候選框)——這時候用「範圍是不是幾乎整個包在另一個候選框裡面」來判斷,巢狀包含就只留 FastSAM 自己比較有信心的那個,避免同一個物件被重複輸出、或者物件的局部細節被誤當成一個獨立物件送去比對。

**第二步(DINOv2/embedding):「這個物體長什麼樣子,用一組數字描述?」**
把裁出來的那個物體的照片,轉成一組高維度數字(向量),外觀相近的物體(材質、形狀、顏色、花紋接近)算出來的向量在空間中的距離也會相近。DINOv2 同樣是通用視覺模型,沒看過我們自己的夾子、瓶蓋長什麼樣,純粹是「兩張照片看起來像不像」的量化。
大致上怎麼做:每個候選框裁出來時故意比框本身留一點邊界(避免物件邊緣剛好被切掉、缺了一角反而看起來不像自己);裁下來的小圖縮放成固定大小、把顏色數值調整到模型習慣的範圍(避免不同曝光/解析度的照片被不公平地比較);最後丟進 DINOv2 產生那組代表外觀的向量。

**第三步(比對 catalog/特徵池):「這組數字,最像我們手上哪個已知物品?」**
不是「分類模型判斷這是類別 A」,是「這組向量,離使用者自己上傳的哪些參考圖向量最近」——本質是相似度搜尋,不是訓練好、固定住的分類頭。這也是為什麼新增一個物品類別不用重新訓練模型:只要多拍幾張參考圖、算出向量丟進特徵池,下一次比對自然就會考慮到它。
大致上怎麼做:使用者每上傳一張參考圖,也是走同一套「裁切 + DINOv2」流程先轉成向量存起來,當作「這個物品長怎樣」的一筆樣本;同一個物品可以存好幾張不同角度/顏色/光線的參考圖,不會先把它們平均成單一代表向量。真正比對時,候選框的向量拿去跟特徵池裡**每一筆**樣本分別算相似度,取全域最高分那筆,那筆樣本所屬的物品就是這個候選框的最佳猜測——不用管最高分是從哪張參考圖來的,只要「有一張夠像」就算數。

**第四步(threshold):「這個相似度,夠不夠讓人相信這就是它?」**
不是模型自己算出來的信心分數,是使用者自己設的容忍線——同一個相似度分數,門檻設鬆一點就會被接受、設嚴一點就會被打回 unknown,是風險/精確度的取捨,不是辨識本身對不對。
大致上怎麼做:系統一律先把「最高分猜測」跟「這個分數有沒有超過目前的門檻」兩者都算出來、都回傳,不會自己武斷地二選一——要不要採信最高分那個猜測,交給拿到結果的一方自己決定(可以直接用系統建議的門檻,也可以套自己的標準)。

## 環境

- Python 3.14.6,`.venv/`
- **執行期(可進 Docker)**:只需要 `onnxruntime` + `numpy` + `Pillow`,不需要 PyTorch/torchvision/ultralytics
- **開發期(不進 Docker)**:`torch`/`torchvision`/`ultralytics`,只有 `export_dino.py`/`export_fastsam.py` 這兩支一次性匯出腳本需要

## 檔案結構

```
執行期:
  objectness.py      FastSAM ONNX 推論 + 後處理 + containment 去重, 找候選物件
  embedding.py        DINOv2 ONNX 推論 + 純 PIL/numpy 前處理, 算 embedding
  catalog.py           compute_prototype()(單一類別代表向量)+ build_catalog()(批次建目錄)
  recognize.py          組裝 objectness + embedding + catalog 比對 + threshold + 視覺化
  build_catalog.py    CLI: 呼叫 catalog.build_catalog() 存成 catalog.json

開發期(不進 Docker):
  export_dino.py       匯出 dinov2_vits14.onnx
  export_fastsam.py    匯出 FastSAM-s.onnx

模型/資料產物:
  dinov2_vits14.onnx, FastSAM-s.onnx, catalog.json
```

## 必須嚴格遵守的規格/設定

這些是已經驗證過(跟 PyTorch 原始版本逐筆核對過 bbox/分數/cosine similarity)的參數,改動前要重新驗證,不要憑感覺調:

### 模型路徑決定順序(`objectness.load_session()` / `embedding.load_session()`)

1. 函數呼叫時明確傳入的 `onnx_path` 參數
2. 環境變數:`FASTSAM_ONNX_PATH`(FastSAM)、`DINOV2_ONNX_PATH`(DINOv2)
3. 預設值:錨定在對應 `.py` 檔案自己的資料夾(`Path(__file__).resolve().parent`),不依賴執行時的當前工作目錄

### FastSAM ONNX 推論參數(`objectness.py`)

- 輸入 `images` `[1,3,640,640]` float32,letterbox 前處理(等比例縮放+灰色 114 補邊)。原本是 1024,已改成 640(見下方「FastAPI 化」章節的解析度調整記錄),mask prototype 的形狀跟著 IMGSZ 等比例縮放,程式碼裡不寫死
- `CONF_THRESH = 0.4`、`IOU_THRESH = 0.6`(NMS)、`CONTAINMENT_THRESH = 0.85`(自訂巢狀去重)
- containment 去重規則固定用 **highscore**(巢狀時留 FastSAM confidence 較高的),不要換成 smaller,見下方比較實驗結論

### DINOv2 ONNX 前處理(`embedding.py`)

- RGBA 一律先合成白底轉 RGB
- resize 短邊到 256(`Image.BICUBIC`,長邊用 `int()` 無條件捨去,不是 round)
- center crop 224(用 `round()`,不是 `int()` 捨去)—— 這兩個捨入方式刻意對齊 torchvision 的行為,兩者不一致會導致非正方形圖片算出的向量跟原始 PyTorch 版本對不上
- normalize: `mean=(0.485, 0.456, 0.406)`, `std=(0.229, 0.224, 0.225)`(ImageNet 標準值)
- 輸出 384 維(`dinov2_vits14`)

### recognize.py 參數

- `CROP_PADDING_RATIO = 0.1`:候選框裁切時往外多留的比例(框自身寬高的比例,不是像素、不是整張圖比例)。**不要調超過 0.3~0.4**,見下方 padding 掃描實驗結論
- `SCORE_THRESHOLD = 0.3`:cosine similarity 最高分低於此值 → 標記 `unknown`,不強制歸類

### images/ 資料夾慣例(few-shot 參考圖,給 `build_catalog.py` 掃描用)

- `images/<類別名>/` 底下每個子資料夾 = 一個類別,**資料夾名必須是英文**(視覺化畫框標籤用 PIL 預設字型,不支援中文,會變亂碼/方框)
- 只收檔名是純數字的圖片(例如 `1.png`),排除像 `original.webp` 這種未裁切的來源圖

### catalog.json schema

```json
{ "類別名稱": [384維向量的浮點數陣列], ... }
```

扁平結構,不存圖片來源資訊(檔名/路徑)—— 圖片本體管理是檔案系統/物件儲存的責任,不是這份資料的責任(見下方討論)。

## 後處理流程步驟摘要

### `objectness.find_objects(image)`(FastSAM ONNX)

1. letterbox:等比例縮放到 1024×1024 內,灰色(114,114,114)補邊
2. ONNX Runtime 推論 → `output0 [1,37,21504]`(37 = 4 bbox + 1 conf + 32 mask 係數)、`output1 [1,32,256,256]`(32 個 mask prototype)
3. 信心過濾:`conf > CONF_THRESH`
4. bbox 格式轉換:cxcywh → xyxy(仍在 letterbox 後的 1024 座標系)
5. NMS(貪婪演算法,邏輯同 `torchvision.ops.nms`):分數高的留,跟它 IoU 超過 `IOU_THRESH` 的低分丟掉
6. mask 解碼:mask 係數 `(N,32)` × mask prototype `(32,256*256)` → sigmoid → reshape `(N,256,256)`
7. bbox 座標換算回原圖:扣掉 letterbox padding、除以縮放比例、clip 到原圖範圍
8. mask 換算回原圖:256×256 放大到 1024 letterbox 畫布 → 裁掉補邊 → 縮回原圖尺寸 → 裁到 bbox 範圍 → threshold 0.5 二值化
9. containment 去重(見上方規格):巢狀重複時留信心分數較高的候選

回傳 `list[DetectedObject]`(`bbox`、`objectness_conf`、`mask`)。

### `embedding.embed(image)`(DINOv2 ONNX)

1. RGBA → 白底合成 RGB
2. resize 短邊到 256、center crop 224
3. normalize(ImageNet mean/std)
4. ONNX Runtime 推論 → 384 維向量

### `recognize.recognize(image, catalog)`

1. `objectness.find_objects(image)` 拿到候選物件列表
2. 每個候選框裁切(含 `CROP_PADDING_RATIO` 留白)→ `embedding.embed()` 算向量
3. 跟 `catalog` 裡每個已知類別的 prototype 算 cosine similarity,取最高分
4. 最高分 < `SCORE_THRESHOLD` → 標記 `unknown`,否則採用該類別名稱
5. 回傳 `list[RecognizedObject]`(`bbox`、`class_name`、`score`、`all_scores`、`mask`、`objectness_conf`),不畫圖 —— 畫圖是 `draw_recognition()` 的責任,兩者分開

## 試過的方案與結論

### 1. containment 去重規則比較:highscore / smaller / 全保留+相似度排序

在測試圖 `images/eletronics_2.jpg` 上跑三種規則,比較覆蓋率與正確率:

| 規則 | 說明 | 結果 |
|---|---|---|
| **highscore**(採用) | 巢狀時留 FastSAM confidence 較高的 | 整體最平衡,四個已知類別大多正確辨識 |
| smaller | 巢狀時留面積較小(較精細)的 | 傾向「pinpoint 準但保守」,容易只框到物件局部(例如只框到接腳、不含機身),導致原本用 highscore 能辨識的物件(黃色 LED、部分按鍵開關)反而變成 unknown |
| 全保留(不去重)+ 用 DINOv2 相似度排序決定去重 | 讓 embedding 分數本身決定巢狀時留誰,而不是 FastSAM 分數 | 沒有實質改善,且引入新的誤判(某候選框被誤判成錯的類別,原本會被過濾掉的爛框反而因為換了排序依據重新冒出來) |

**結論**:三種規則都無法解決「候選池裡根本沒有正確候選框」的案例(見下方電位器案例)—— 排序規則只能在「正確候選框存在但被過濾掉」時有用,無法無中生有生出一個 FastSAM 從未提出過的候選框。`highscore` 維持為預設。

### 2. CROP_PADDING_RATIO 掃描:0.1 / 0.3 / 0.4 / 0.45 / 0.6 / 1.0

`CROP_PADDING_RATIO` 是候選框自身寬高的比例,不是固定像素、也不是整張圖比例。

- 小幅提高(0.1→0.3~0.4)對「框太保守、只差一點沒框滿」的物件有幫助(按鍵開關分數明顯回升)
- 過度提高(0.6~1.0)出現**副作用**:框本身較大的候選框(例如紙卡標籤),padding 也等比例放大,裁切範圍膨脹到吃進旁邊完全不相干的候選框內容,造成 embedding 被污染、產生新的誤判(紙卡被誤判成 `led` / `rotary_potentiometer`)。用疊圖(黑色細框 = 實際裁切範圍 vs 彩色粗框 = 原始 bbox)肉眼驗證確認了這個污染現象
- **結論**:`CROP_PADDING_RATIO` 用固定比例本身有這個副作用(大框跟著等比例放大留白),`0.1~0.3` 是相對安全的範圍,不建議繼續往上調

### 3. 已知限制:緊貼/觸碰物件群組(電位器 4 顆案例)

測試圖裡 4 顆旋轉電位器彼此貼很近,拆解 FastSAM 原始候選(去重前)後發現:

- 有 2 顆電位器各自有乾淨的單一候選框(機身/接腳分開或合併都有候選)
- 另外 2 顆只有兩種候選:一個是單顆大小的候選(但形狀/範圍不乾淨,embedding 分數低,約 0.05~0.08)、一個是明顯合併兩顆的大候選(面積約是單顆的 2 倍)
- **這是 FastSAM 分割階段的候選不足,不是後處理(containment 規則/padding)能解的**,不管用哪種去重規則或 padding,最後都只能在「這兩個都不理想的候選」之間選,無法變出一個乾淨切開兩顆的候選框

**未來方向(尚未實作,先記錄)**:

- 用 **watershed** 處理疑似合併的 mask:watershed 是 pixel-level 的區塊分割(不是切 bbox),對已經判定「疑似合併」的 mask 算 distance transform,找局部極大值當種子點切割,切完後才從每塊分割結果反推出新的 bbox
- 觸發時機:對 containment 關係中的候選框跑 distance transform,**local maxima 數量 ≥ 2 才觸發 watershed 切割,只有 1 個就維持原狀不切**,避免誤傷形狀複雜但本來就是單一物件的候選框
- 何時該接在 pipeline 的哪裡:**必須在 containment 去重之前**,對原始候選池做疑似合併判斷跟 watershed 處理,不能等 containment 篩選跑完才做 —— 因為不管 highscore 或 smaller 規則,篩選過程都可能已經把合併框本身丟掉

**更新(FastSAM 改成 640 解析度後)**:上面的分析是在 1024 解析度下做的。改成 640 之後(見「FastAPI 化」章節),實測這張圖的 4 顆電位器**全部都拿到乾淨的單一候選框、分類也都正確**(`rotary_potentiometer` 從 2 顆變 4 顆,`compare_fastsam_resolution.py` 有量到這個數字)。推測是 mask prototype 解析度跟著變小(256x256→160x160)之後,這批候選的 mask 邊界剛好切得更乾淨,containment 去重也沒有再誤判成合併——但這比較像運氣好的副作用,不是刻意調出來的,換一批物件間距更近的圖片,結果不保證一樣好。上面的 watershed 方向還是值得保留當作備案,不能因為這次剛好改善就當作問題已經徹底解決。

### 4. ONNX 化:PyTorch → ONNX Runtime

- FastSAM(`ultralytics` 內建 `.export(format="onnx")`)跟 DINOv2(`torch.onnx.export`,需要包一層 wrapper 避免 `forward(*args, **kwargs)` 簽名把多餘的 `masks` 輸入捕捉進計算圖)都成功匯出,逐筆核對過 bbox/mask 面積/embedding cosine similarity 跟原始 PyTorch 版本幾乎一致(cosine similarity 1.0,誤差在浮點數精度等級)
- DINOv2 的前處理(resize/center_crop/normalize)也已經用純 PIL/numpy 重寫,不依賴 torchvision,精確對齊 torchvision 的捨入方式(見上方規格)
- 執行期完全不需要 PyTorch/torchvision/ultralytics,只有匯出模型的開發工具需要

### 5. FastAPI 化:模型生命週期 + OpenVINO EP + DINOv2 INT8 動態量化

**優化嘗試速覽**(細節見下方各條, 時間都是 DINOv2 或 FastSAM 單一階段的 `session.run()`/`find_objects()` 耗時, 不是整個 `/predict/new` 總時間):

| 項目 | 縮短多少% | 有沒有採用 | 為什麼 |
|---|---|---|---|
| DINOv2 batch 推論(`embed_batch()`) | ~0%(在雜訊範圍內, 記憶體反而多 200-400MB) | ❌ 沒採用 | CPU 單張呼叫就已經吃滿所有核心(intra-op 平行化), batch 沒有多餘平行資源可用, 只是換個方式排列同樣運算量 |
| OpenVINOExecutionProvider(FastSAM+DINOv2, FP32) | ~8-12% | ✅ FastSAM 採用, DINOv2 後來因為量化不相容而放棄 | 對 Intel 硬體(部署目標 N100)有實質優化, 相容性也沒問題(FastSAM 這邊) |
| 明確指定 `num_of_threads=4`(模擬 N100 核心數) | **-8~10%(變慢)** | ❌ 沒採用, 已移除設定 | 預設值在這台筆電上本來就抓得比手動限制 4 threads 好, 限制反而砍掉可用的平行資源 |
| DINOv2 INT8 動態量化 | ~41%(即使失去 OpenVINO 加速) | ✅ 採用 | 淨賺(量化的加速幅度 > 失去 OpenVINO 的損失), 分類結果只有 3.5% 翻盤(且多數是邊界案例) |
| FastSAM INT8 動態量化 | 未實測 | ❌ 沒嘗試 | FastSAM 是 CNN(Conv 為主), ONNX Runtime 動態量化主要加速 MatMul, 預期效益有限, 且可能重演 OpenVINO 不相容的問題, 風險報酬不對稱, 評估後決定不做 |
| FastSAM 解析度 1024→640 | ~55% | ✅ 採用 | 目前最高 CP 值的一項:完全相容 OpenVINO, 準確度實測沒有類別崩掉(部分類別甚至微升) |

- **模型生命週期**:拿掉 `objectness.py`/`embedding.py` 原本 module-level 的懶載入單例(`global _session`),`load_session()` 改成單純讀取回傳、不快取。改由 FastAPI `lifespan` 明確建立 session(FastSAM + DINOv2 各一次)、讀一次 `catalog.json`,一起放進 `model_holder`,route handler 呼叫 `recognize()` 時把 session/catalog 顯式注入,不再依賴模組內的隱藏全域狀態
- **DINOv2 ONNX 改成 dynamic batch axis**:原本匯出時 batch 維度寫死 1(`export_dino.py` 沒設 `dynamic_axes`),導致沒辦法真的做 batch 推論。補上 `dynamic_axes={"input": {0: "batch"}, "embedding": {0: "batch"}}` 後重新匯出、驗證過 batch=1/batch>1 的輸出都跟原本一致(cosine similarity 1.0)
  - 但**batch 推論實測沒有幫助**:在 N100 的目標情境下,CPU 是靠 intra-op 平行化吃滿核心,單張呼叫本來就已經用滿所有核心,batch 起來只是換個方式排列同樣的運算量,固定開銷省下來的量遠小於記憶體多付出的代價(同一張測試圖,batch 版本記憶體會多出 ~200-400MB,速度沒有統計顯著的改善)。目前正式版是 sequential(逐張呼叫 `embed()`),`embed_batch()` 保留在 `embedding.py` 但沒被呼叫,`recognize.py` 裡的 batch 呼叫段落用註解保留、方便之後需要時切回去
  - **拿掉 postgres 之後重測過一次,結論不變**:曾經懷疑閒置的 postgres container 背景心跳可能污染 L3 cache、讓 batch/sequential 的比較失真(見 `docs/辨識服務部署方案.md`)。實際把 postgres 整個移除後(改成單一 container、無資料庫依賴),重新對照一次:sequential 約 1.5-1.7 秒、batch 約 1.8-2.0 秒,batch 依然沒有優勢,結論確認跟之前一致,不是 postgres 造成的假象
- **OpenVINOExecutionProvider**:FastSAM/DINOv2 的 session 都改成 `providers=["OpenVINOExecutionProvider", "CPUExecutionProvider"]`(找不到 OpenVINO 才退回 CPU)。實測 FastSAM+DINOv2(FP32)這段比純 CPUExecutionProvider 快約 8-12%。這個環境的開發機是 AMD(無 VNNI),部署目標 N100 是 Intel(支援 AVX-VNNI),實際到 N100 上的加速幅度預期會更高,不是這台開發機測到的數字上限
- **DINOv2 INT8 動態量化**(`onnxruntime.quantization.quantize_dynamic`):
  - 純看 embedding 向量的 cosine similarity(量化前後同一張圖)掉到 0.88-0.98,比預期的多,`quant_pre_process` 沒有改善這個數字(那個提示對動態量化沒什麼用,主要是給靜態量化用的)
  - 但**用「INT8 catalog 配 INT8 embedding」重新跑一次端到端分類**(不能拿 INT8 向量去比對 FP32 catalog,那樣沒意義),86 個真實候選框(2 張測試照片)裡只有 3 個分類結果不同(3.5%),其中 2 個是 `SCORE_THRESHOLD=0.3` 邊界的低信心案例,只有 1 個是真正的類別混淆(電位器誤判成按鍵開關)
  - **INT8 量化後的模型(QOperator 格式)沒辦法用 OpenVINOExecutionProvider**,載入會直接拋錯(`Error: the graph is not acyclic`),不是優雅 fallback,所以 `embedding.py` 的 `load_session()` 固定只用 `CPUExecutionProvider`
  - 即使失去 OpenVINO 加速,INT8+CPU 實測仍比 FP32+OpenVINO 快 ~41%(35 個候選框:~1657ms → ~980ms),淨賺,已正式採用
  - 模型檔案命名(不管是不是正式在用的, 全部用完整描述詞: 模型_batch軸_精度):`dinov2_vits14_batch_int8.onnx`(正式版, dynamic batch axis + INT8)、`dinov2_vits14_batch_fp32.onnx`(量化前, dynamic batch axis + FP32, 備份)、`dinov2_vits14_no_batch_fp32.onnx`(最原始, batch 維度寫死 1 + FP32, 備份)
  - 校正/驗證用的腳本:`backend/scripts/quantize_dino.py`(量化 + 向量 cosine similarity 檢查)、`backend/scripts/compare_int8_classification.py`(端到端分類結果比對)
- **FastSAM 輸入解析度 1024 → 640**:`export_fastsam.py` 加上 `FASTSAM_EXPORT_IMGSZ` 環境變數(預設 1024),重新匯出 640 版本。跟 DINOv2 量化不同, FastSAM 是 CNN(Conv 為主), 量化對它效益有限(ONNX Runtime 動態量化主要處理 MatMul, 不太處理 Conv), 所以這裡選解析度而不是量化
  - 準確度:用現有 catalog(INT8 DINOv2)分別跑 1024/640 兩版的端到端分類, 比較兩張測試照片每個已知類別的候選數量, 沒有任何類別崩掉或消失, 大部分持平或微升(例如 eletronics_2.jpg 的已知類別總數 31→34), `unknown` 桶還略減。因為兩種解析度的候選框集合本質上不是同一批(不同 grid/NMS 結果), 沒辦法像 DINOv2 那樣逐一配對比較, 只能看整體統計, 見 `backend/scripts/compare_fastsam_resolution.py`
  - 速度:OpenVINO EP 下實測 ~843ms → ~383ms,快 ~55%(約 2.2 倍),而且**完全相容 OpenVINOExecutionProvider**(不像 INT8 量化那樣會讓 OpenVINO 直接拋錯),已正式採用
  - `objectness.py` 的 mask prototype reshape 原本寫死 `256`(對應 1024 輸入時 proto 剛好是 256x256),改解析度前先修成用 `proto.shape` 動態取得,不然 640 版本(proto 是 160x160)會直接壞掉
  - 模型檔案命名(同上, 模型_解析度_精度):`FastSAM-s_640_fp32.onnx`(正式版)、`FastSAM-s_1024_fp32.onnx`(解析度調整前, 備份)。`backend/models/FastSAM-s.pt` 是重新匯出用的原始權重(可以再拿去試其他解析度)

### 6. 樣本圖背景污染:木紋變成特徵、bbox 修正機制設計

**問題發現**:用 `vision-service/scripts/visualize_result.py` 對照 `/recognize` 的掃描結果,發現硬幣被誤判成瓶蓋。用 `vision-service/scripts/inspect_fastsam_candidates.py` 對參考圖(`vision-service/test/fixtures/`)跑純 FastSAM 候選框檢視(不比對類別,只看候選框本身)後確認兩件事:

- 大多數參考圖裡,真物件的候選框面積遠大於木紋雜訊候選框(實測 peg/coin/bottle_cap 三種都有 10 倍到近 100 倍的差距),「挑面積最大的候選框」這個啟發式規則整體可靠
- 但有反例:`peg_purple_1.jpg` 淺紫色夾子跟深色木桌對比度太低,FastSAM 完全沒能把夾子本體切成一個連續候選框,「面積最大」的候選框反而框到夾子鏤空處中間的黑色縫隙(area=34140),不是夾子本體——代表面積啟發式不是萬無一失,需要人工把關這個環節

**根本原因**:建立樣本時是把整張上傳圖片直接丟給 DINOv2,沒有先裁到物件本體。few-shot 參考圖常見的構圖是「一大片桌面背景 + 中間一個很小的物件」,DINOv2 前處理(resize 短邊 256 + center crop 224)幾乎原封不動吃進整張構圖,背景占比遠遠壓過物件本身——拍攝方式類似的不同物件(硬幣 vs 瓶蓋,都是「圓形物件置中、四角是同一張木桌的木紋」)因此在 embedding 空間裡意外地相近,分錯類別。

**修正方向(設計已定案,尚未實作)**:

- 建樣本時先跑一次 `find_objects()`(FastSAM),挑面積最大的候選框,套用現有 `CROP_PADDING_RATIO` 裁切後才丟給 DINOv2 算 embedding,跟 `/recognize` 時的裁切邏輯一致;找不到候選框時 fallback 回整張圖
- 因為面積啟發式不保證每次都對(見上方紫夾子案例),需要人工修正機制:`recognition_samples` 新增 `predicted_bbox`(自動偵測結果,寫入後不變)/`final_bbox`(目前生效的框,可被人工修正)兩欄,建立時兩者相同;原圖照舊完整保留(不是只存裁切後的結果),之後 `PATCH /samples/{id}` 送新的 bbox 時才有東西可以重新裁切、重算 embedding(見 `docs/schema.md`/`docs/辨識服務API.md`)
- `predicted_bbox != final_bbox` 的紀錄未來也是 FastSAM fine-tune 的訓練訊號(教模型認得「低對比度物件也要切出完整輪廓」這類案例),但這是獨立於 `recognition_predictions`(掃描結果的 predicted/final)之外的另一批訊號——兩者代表不同的錯誤來源(`recognition_predictions` 主要是物件之間的 containment 合併;`recognition_samples` 主要是物件跟背景的分割不足),之後真的做 fine-tune 資料匯出時要標記來源分開看,不要混著訓練

**討論過但現階段不採用的替代方案:patch token mask 篩選**

概念:DINOv2 ViT 除了最終 pooled 的 CLS token,每一層還有各個 patch 各自的 token(呼叫 `forward_features()`,不是現在匯出用的 `forward()`)。可以把 FastSAM 的 pixel mask 降採樣到 patch grid 解析度,只挑「mask 判定為前景」的 patch token 平均當最終向量,理論上比裁 bbox 更精細——能濾掉 bbox 範圍內、但仍是背景的部分(例如物件鏤空處露出的木紋),bbox 裁切這種矩形層級的做法處理不了這個。

現階段不做的原因:

1. 解決的是跟裁 bbox 不同層次的問題——只能去除「候選框大致正確、但框內仍殘留背景」的污染,沒辦法修正「候選框根本框錯地方」(紫夾子案例屬於這一種),後者只能靠人工修正框解決,兩個問題要分開處理,不是同一個技術能一次搞定
2. ViT 每一層都是全域 self-attention,深層的 patch token 在計算過程中早已跟背景 patch 互相混合過資訊,不是切得乾乾淨淨的純前景特徵,實際效果不會像理論描述得那麼絕對
3. 現在的 ONNX 匯出(`export_dino.py`)只留 CLS token 輸出,沒有 patch token 頭,要用這個方法得重新匯出模型、還要處理 mask 降採樣對齊 patch grid 的細節,工程量比裁 bbox 大得多,且效果未經驗證

**結論**:先做「裁 bbox + 人工修正機制」,這兩個能處理目前實際觀察到的兩種問題(背景占比過大、候選框整個框錯)。patch mask 篩選留著當之後的加分項——真的把前兩個做完、還是覺得同一個 bbox 內背景干擾明顯,再考慮值不值得投入,而且要做的話應該先小規模驗證有沒有實質改善,不要沒驗證就直接換掉現在的 CLS token 方案。

### 7. 用人工標註 ground truth 驗證 bbox 修正效果, 意外發現 `/recognize()` 裁切的角落污染問題

**方法**:針對兩張 peg/bottle_cap 混合場景照(`scene_1.jpg`/`scene_2.jpg`)人工標註 ground truth(`vision-service/test/scene_1_2_result_label.csv`,格式跟舊的 `eletronics_2.csv` 一致:`label_name,bbox_x,bbox_y,bbox_width,bbox_height,image_name,image_width,image_height`),寫 IoU 比對腳本(IoU ≥ 0.5 判定為同一物件)分別評估「第 6 節的樣本 bbox 修正」生效前後的 `/recognize()` 結果,而不是肉眼比對——**這次過程中肉眼比對已經證實不可靠**(在密集場景照裡,重疊/相鄰標籤跟框對應錯誤好幾次,詳見下方教訓)。

**驗證結果(排除 `cap` vs `bottle_cap` 命名差異這種假陽性後)**:

| | 修正前 | 修正後 |
|---|---|---|
| `scene_1.jpg` 真分類錯誤(藍夾子被判成 purple) | 1 個(score 0.60) | 0 個(該候選框改判 blue, score 0.64) |
| `scene_2.jpg` 真分類錯誤(藍夾子被判成 purple) | 1 個(score 0.73) | 依然存在(score 反而升到 0.79) |
| 背景候選誤判成已知類別(硬幣/卡片/紙盒等) | `scene_1` 4 個 / `scene_2` 6 個 | `scene_1` 4 個(不變)/ `scene_2` 4 個(2 個弱誤判分數掉到門檻以下, 變回 unknown) |

**判定門檻(`SCORE_THRESHOLD`)重新評估**:用這份修正後的乾淨數據檢查,所有正確辨識(TP)分數都 ≥ 0.64,所有背景誤判分數都 ≤ 0.54,中間有清楚的空隙——`0.6` 是這份測試資料上可行的門檻,能濾掉全部背景誤判又不會誤殺任何正確辨識。但**這個門檻救不了 `scene_2` 那個持續存在的分類錯誤**(0.79 分數已經很高,不是訊號太弱被門檻擋住的問題,是真正的方向性混淆),門檻調整跟分類混淆是兩個獨立問題。

**意外發現:`scene_2` 那個分類錯誤的根本原因**——裁出實際被送進 DINOv2 的那個 bbox 範圍(`[435.87, 1301.49, 1035.65, 1997.51]`)來看,右下角真的裝進了一塊相鄰的紫色夾子、左上角帶到硬幣邊緣。這支藍夾子是斜放的,但 bounding box 永遠是正矩形,物件跟裁切框的方向不一致時,矩形的角落必然會裝到旁邊其他東西——這次裝到的剛好是「有意義但錯誤的另一個物件」,不是無害的木紋雜訊,污染程度比第 6 節的木紋案例更嚴重。

**這重新打開了第 6 節結尾否決掉的 patch mask 篩選方案,但適用範圍要修正**:
- 第 6 節討論的是**建樣本時**的木紋污染,背景是無意義雜訊,裁緊 bbox 就能大幅改善,patch mask 的邊際效益不高,所以當時決定不做
- 這次是 **`/recognize()` 掃描時**的裁切,問題性質不同:混進來的是「有語意、會誤導分類的另一個物件」,而且是矩形裁切框對付旋轉物件的天生幾何限制,不管 padding 留多少都躲不掉——FastSAM 本來就有算出貼合旋轉角度的 pixel mask,如果裁切後、丟進 DINOv2 前先用這個 mask 蓋掉「矩形範圍內但不屬於這個物件」的像素,理論上能根治這個案例,不是像 bbox 裁切一樣只能減少

**尚未實作,只記錄結論**:值得針對 `/recognize()` 的裁切步驟(不是建樣本步驟)重新評估 patch mask 篩選,但要先解決第 6 節提過的工程門檻(現在的 ONNX 匯出沒有 patch token 輸出)。

**教訓:肉眼比對密集場景圖不可靠**——這次過程中我(協助分析的一方)至少誤讀了兩次:一次是把疊在一起的標籤跟框配對錯誤、把某個背景誤判當成正確辨識;一次是直接裁錯 bbox 座標去驗證污染假設,拿到一張乾淨的裁切圖就以為假設不成立,後來才發現裁的根本不是使用者說的那個候選框。物件數量一多、標籤位置重疊,肉眼掃過去做判斷的錯誤率會明顯升高,有 ground truth 就該用程式比對,不要靠肉眼在複雜圖片上找答案。

### 8. 效能優化:containment dedup 改用 proto 解析度、移除沒人用的全解析度 mask

`find_objects()` 判斷候選框是否為巢狀重複(見「必須嚴格遵守的規格」的 containment 說明),原本實作是先把每個候選框的 mask 從 proto 解析度(例如 160×160)放大回**原圖完整解析度**,再逐對候選框算「交集/較小面積」的比例。手機拍的照片動輒 4000×3000(1200 萬像素),候選框一多,這步變成整條 pipeline 最慢的環節。

**優化 1:dedup 直接在 proto 解析度上比較,不放大**。containment 比例是尺度無關的比值,不需要放大到原圖解析度才能算,同一對候選框的判斷成本從 O(W×H) 降到 O(proto_h×proto_w)。

**優化 2:發現「放大到原圖解析度」這個全解析度 mask 從頭到尾沒人用過**——`recognize.py`/`sample_ops.py` 都只用 `bbox` 去裁切,`DetectedObject.mask` 算出來後沒有任何下游邏輯讀取它。實測這個沒人用的全解析度放大步驟,占掉優化 1 之後 `find_objects()` 剩餘耗時的 **85%**(測試圖 18 個存活候選框,合計 1574ms / 總耗時 1848ms),直接砍掉整個全解析度 mask 計算,`DetectedObject` 也拿掉 `mask` 欄位。

**實測效果**(`test/fixtures/scene_1.jpg`/`scene_2.jpg`,4000×3000 手機照片,`find_objects()` 單獨計時):

| | 優化前 | 優化 1(proto dedup) | 優化 2(移除全解析度 mask) |
|---|---|---|---|
| scene_1 | 5816 ms | 1856 ms | 212 ms |
| scene_2 | 5458 ms | 1370 ms | 239 ms |

總計約 **25-27 倍**。優化 1 在 scene_2 造成一個候選框差異(proto 解析度的量化誤差,讓一個在全解析度下勉強不算巢狀重複的小候選框,被判定成重複而濾掉)——用第 7 節的 ground truth IoU 比對驗證過,這個候選框本來就低於辨識門檻(`meets_threshold=false`),對 `/recognize` 最終輸出的 TP/WRONG_CLASS/FN 統計完全沒有影響。

**未來要做 patch-token masking(見第 6 節)的話,應該從這裡優化後留下的 proto 解析度 mask 資料衍生,不是重新算全解析度版本**——patch mask 最終要的解析度(ViT patch grid,例如 16×16)遠低於 proto 解析度,proto 解析度的資訊量綽綽有餘;而且「對應到裁切區域、縮到 patch grid」這件事本來就該在真正裁切候選框當下才做(那時候才知道最終裁切範圍),不是在 `find_objects()` 階段預先算好、算完又可能沒用到。

## 其他決策

- few-shot 參考圖:乾淨白底單物件特寫,3~5 張起跳,涵蓋角度變化;若類別內有顏色變化(例如不同顏色 LED)且要當同一類別,要混色拍,不能只拍一色當代表,否則平均後的 prototype 會偏向某個顏色、對其他顏色泛化差
- DINOv2 不是完全色彩不敏感(訓練時的 color jitter 只是增加穩健度,不是消除顏色訊號),顏色差異在 embedding 空間裡仍是有意義的特徵,分類粒度(要不要分顏色)要事先想清楚
- 視覺化用 `color_mode="instance"`(每個實例隨機色),不能用預設的 `color_mode="class"`(FastSAM 只有一個 class,同色會疊在一起分不清楚)
- 命名:`embedding` = 單張圖算出來的向量;`prototype` = 某類別多張範例圖 embedding 平均出來的代表向量(few-shot learning 標準用語);`catalog` = 所有已知類別 + 各自 prototype 放在一起、給 `recognize()` 做相似度比對用的整個集合(對應人臉辨識系統的 gallery 概念,選用更通俗的說法)
- Session/模型物件已經搬進 FastAPI 服務,`lifespan` 明確建立、注入下來,不再依賴隱藏的全域狀態(見上方「FastAPI 化」章節)
- 圖片本體不進資料庫:資料庫/catalog 只存 embedding 向量(+ 之後可能的 id/classname 等 metadata),圖片本體交給檔案系統或物件儲存(S3 這類),資料庫只存參照路徑/key,不存位元組資料
